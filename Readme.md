# Этапы развития проекта
 - *Bootloader* : **расширить загрузчик: загрузка ядра с диска, переключение в protected mode**
 - *Kernel* : **Базовое ядро на Си**
 - *VGA driver* : **Вывод текста на экран**
 - *GDT* : **Глобальная таблица дескрипторов**
 - *PMM* : **Физический менеджер памяти**
 - *VMM* : **Виртуальный менеджер памяти / Paging**
 - *kheap* : **Аллокатор кучи ядра**
 - *Drivers* : **VGA, Keyboard, Timer, Disk, Serial**
 - *IDT* : **Таблица дескрипторов прерываний**
 - *IRQ* : **Обработка прерываний, таймер**
 - *Shell* : **Мини-терминал с командами help/clear/about/mem/heaptest/disk**
 - *Serial* : **Логирование в COM1, чтобы можно было дебажить без VGA**
 - *Mini clib* : **Свои string/stdio/stdlib/ctype/mem, потому что libc в freestanding мире не прилетает с небес**
 - *Build* : **Makefile, flat binary kernel.bin, сборка в сырой floppy-like os.img**
 - *fs and etc* : **Дальнейшие шаги масштабирования**

## Для чего всё это?
У меня есть желание проверить как всё работает под капотом, после прочтения различной литературы вроде Таненбаума, появилось огромное желание попробовать спуститься вниз по абстракциям на практике. Это лишь начальный этап который сподвигнет меня углубиться в примитивы ОС, а дальше будут попытки накостылить сюда различные штуки.

## Что уже есть сейчас?
Сейчас проект умеет:
 - **Грузиться с первого сектора диска**: BIOS отдаёт управление boot sectorу по `0x7C00`, а он уже подтягивает ядро с диска
 - **Переходить в protected mode**: включается A20, грузится GDT, выставляется PE-бит в `CR0`, дальше far jump и жизнь в 32 битах
 - **Запускать C kernel**: `kernel_entry.asm` чистит `.bss`, зовёт `kernel_main`, а дальше всё уже более-менее похоже на нормальный freestanding C
 - **Работать с VGA text mode**: вывод, переносы строк, backspace, скролл, аппаратный курсор.
 - **Иметь IDT/ISR/IRQ**: есть таблица прерываний, asm-stub'ы, обработчики исключений и IRQ-линии
 - **Принимать клавиатуру через IRQ1**: scancode'ы попадают в circular buffer, потом терминал вытаскивает оттуда ASCII
 - **Тикать таймером через PIT/PIC**: PIT настроен на 100 Hz, IRQ0 идёт через remapped PIC.
 - **Включать paging**: identity mapping первых 4 MB + VGA, загрузка `CR3`, PG-бит в `CR0`.
 - **Выделять память**: PMM раздаёт физические страницы, VMM мапит виртуальные адреса, kheap даёт `kmalloc/kfree`
 - **Тыкать ATA PIO**: `IDENTIFY`, чтение/запись секторов, вывод инфы по primary master/slave через команду `disk`
 - **Писать в serial**: терминал дублирует вывод в `COM1`, поэтому `make run-serial` сильно приятнее когда экран внезапно умер.

## Карта проекта
Чтобы не теряться в директориях::
 - `boot/boot.asm` 512-байтный стартовый сектор, real mode, загрузка ядра через BIOS `int 0x13`, включение protected mode.
 - `boot/gdt.asm` минимальная GDT под flat memory model: null/code/data.
 - `kernel/kernel_entry.asm` — вход в ядро после bootloader'а, чистка `.bss`, вызов `kernel_main`.
 - `kernel/linker.ld` раскладка ядра в памяти, старт по `0x10000`, символы `__bss_start`, `__bss_end`, `kernel_end`.
 - `kernel/kernel.c` основной порядок инициализации и мини-терминал.
 - `kernel/idt.*`, `kernel/isr.*`, `kernel/interrupt.asm` — исключения, IRQ, сохранение регистров, `iret`.
 - `kernel/pmm.*` bitmap физических страниц.
 - `kernel/vmm.*` page directory/page table, `map/unmap`, `CR3`, `invlpg`.
 - `kernel/kheap.*` куча ядра поверх paging'а.
 - `drivers/vga.*` текстовый экран 80x25.
 - `drivers/keyboard.*` PS/2 keyboard, scancode set 1, shift/caps/backspace/enter.
 - `drivers/timer.*` PIC/PIT, EOI, ticks/sleep.
 - `drivers/disk.*` ATA PIO primary bus.
 - `drivers/serial.*` COM-порт, сейчас в основном для логов.
 - `clib/` маленькая libc-подобная прослойка, чтобы можно было не писать всё руками каждый раз.

## Как всё стартует?
1. BIOS читает первый сектор `os.img` в `0x7C00` и прыгает туда.
2. Bootloader сохраняет boot drive из `DL`, проверяет A20 и при необходимости включает её через BIOS `int 0x15, AX=0x2401`.
3. Ядро читается с `LBA=1`, сейчас жёстко до `200` секторов, в память по линейному адресу `0x10000`.
4. Есть наивная проверка сигнатуры первых байтов ядра. Это не ELF loader и не нормальная валидация, а скорее костыль-охранник чтобы не прыгнуть в совсем мусор.
5. PIC маскируется, грузится GDT, включается protected mode, дальше far jump на `0x08:init_pm`.
6. В protected mode выставляются сегментные регистры на data selector `0x10`, стек ставится на `0x90000`.
7. Bootloader прыгает в `KERNEL_ENTRY_LINEAR`, то есть `0x10000`.
8. `kernel_entry.asm` чистит `.bss`, зовёт `kernel_main`.
9. `kernel_main` инициализирует serial, IDT, память, диск, PIC/PIT, клавиатуру, включает `sti` и запускает терминал.

## Что можно потыкать в терминале?
После запуска появляется `os>`. Команды пока мега базовые:
 - `help` показать список команд
 - `clear` очистить VGA экран
 - `about` коротко сказать что это кастомное 32-битное hobby OS kernel
 - `mem` показать состояние PMM, paging и kheap
 - `heaptest` прогнать небольшой self-test аллокатора
 - `disk` вывести ATA IDENTIFY по `ata0/ata1`: тип, размер, модель, serial, firmware

Ввод идёт с клавиатуры через IRQ, а вывод дублируется и на VGA, и в serial. Поэтому если запускать через:

        make run-serial

можно смотреть вывод прямо в терминале хоста. Это особенно полезно когда VGA сломался и вообще не понятно это ядро умерло или просто экран перестал обновляться

        cd ~/tmp
        wget https://ftp.gnu.org/gnu/gcc/gcc-13.2.0/gcc-13.2.0.tar.gz

        make run-headless # alias на run-serial
        make clean  # почистить артефакты сборки

## Текущая память
Сейчас всё ещё довольно прямолинейно, но уже есть что разбирать:

 - `0x7C00` - сюда BIOS кладёт boot sector.
 - `0x90000` - стек в protected mode после bootloader'а.
 - `0x10000` - линейный адрес куда bootloader грузит `kernel.bin`, оттуда же стартует `kernel_start`.
 - `kernel_end` - символ из linker script, выровненный на 4 KB. От него начинается физический пул PMM.
 - `0x00000000..0x00400000` — первые 4 MB identity mapped при старте paging'а.
 - `0x000B8000` - VGA text buffer, он тоже должен быть замапплен, иначе после paging'а экран превращается в тыкву.
 - `0x00400000..0x04000000` — виртуальный диапазон kheap. Лимит выглядит как 64 MB, но физически он ограничен тем сколько PMM реально может выдать.

Важный нюанс: `memory_init()` пока вручную считает что usable memory заканчивается на `0x400000`. Это удобно для текущего моего этапа, но это не настоящая карта памяти от BIOS. Нормальная ОС должна спросить карту через E820, зарезервировать ядро/boot/mmio/дырки и только потом отдавать страницы PMM

## Что сейчас ограничивает проект?
 - Bootloader грузит **ровно 200 секторов** ядра. Если ядро вырастет сильнее — будет грустно и не очевидно почему.
 - Ядро сейчас **flat binary**, без ELF-заголовков, секций, символов и нормального loader'а.
 - PMM не знает настоящую карту памяти, а живёт в мире `kernel_end..0x400000`.
 - Исключения пока печатают только название и уходят в `hlt`. Для page fault очень хочется печатать `CR2`, `err_code`, `EIP`, `CS`, `EFLAGS`.
 - ATA драйвер работает только с primary bus и PIO polling. Для учебного этапа ок, для нормальной жизни хочется хотя бы аккуратный block device layer.
 - Клавиатура — US раскладка и базовые scancode'ы, без полноценной обработки extended-клавиш.
 - В `clib/src/stdlib.c` есть отдельный игрушечный `malloc` на статическом буфере, а в ядре основной путь — `kmalloc/kfree`. Это надо будет привести к одной политике, чтобы потом самому себя не подставить.
 - Нет FS, VFS, процессов, scheduler'а, user mode, syscall'ов. То есть это пока kernel playground, а не ОС в смысле "запускаю программы".

## Куда копать дальше?
Мой текущий вектор такой: сначала перестать жить на константах, потом сделать диск нормальным, потом уже потихоньку лезть в userland. Иначе можно быстро собрать башню из костылей, которая будет абы как работать, но будет копиться лютейший техдолг который я буду разгребать примерно никогда кэк (хотя можно все делигировать нейронке)

1. **Стабилизировать дебаг**

   Добавить нормальный `klog` поверх serial + VGA, сделать `panic()` с регистрами, отдельный handler для page fault с чтением `CR2`. Ещё полезно добавить Makefile targets под QEMU debug: `-d int,cpu_reset`, `-no-reboot`, `-no-shutdown`, возможно `-s -S` для gdb. Это не прям фича, но оно окупается каждый раз когда ядро решает умереть молча

2. **Переделать память на E820**

   В real mode bootloader должен получить memory map через BIOS `int 0x15, EAX=0xE820`, положить её в известное место и передать ядру и потом PMM должен инициализироваться не по `0x400000`, а по реальным usable ranges. Параллельно нужно еще научиться нормально резервировать само ядро, bitmap, page tables, VGA, BIOS, MMIO.

3. **Сделать block layer**

   Сейчас `disk_read/disk_write` это сразу ATA. Лучше ввести слой типа `block_device_t`: read/write sector, sector size, sector count. Тогда фс не будет знать, ATA там снизу, ramdisk или что-то ещё

4. **Первый filesystem**

   Самый веротяный следующий шаг это read-only FS. Есть два пути:
   - `tarfs/initrd` - он проще и быстрее, можно положить файлы рядом с ядром и научиться читать имена/содержимое
   - `FAT12/FAT16` - он чуть сложнее, зато хорошо ложится на floppy-like образ и учит реальным структурам диска

    Пока хз что использовать, как только появится свободное нормальное время и желание изучить как писать аж файловую систему, то начну наверное с чего попроще.

5. **VFS и shell-команды**

   После первой фс можно добавить уже `ls`, `cat`, `stat`, `readsector`, возможно даже `hexdump`, но всё таки повременю наверное, а вот `ls`, `cat`, `stat` я уже +- знаю как писать

6. **User mode и syscalls**

   Дальше уже GDT с ring3-сегментами, TSS для переключения стека, `int 0x80` или отдельный syscall gate, таблица сисколлов, копирование данных user/kernel

7. **ELF loader, процессы, scheduler**

   Когда есть фс и сисколы, можно грузить ELF, создавать address пространство, делать простейший round-robin scheduler по таймеру. И вот на этом шаге наконец то проект начнёт превращаться из ядра с терминалом в маленькую ОС.

---

- **Что такое А20?**

Если говорить просто: это переключатель, который позволяет процессору видеть больше 1 МБ оперативной памяти. Почему так? Всё просто, наш любимый Х86. В первых процессорах Intel 8086 было всего 20 адресных линий (от A0 до A19). Это позволяло адресовать ровно 2^20 байт = 1 МБ.
Позже начали появляться новые процессоры и надо было оставить обратную совместимость, старые программы полагались на wrap-around памяти. Если они обращались к адресу чуть выше 1 МБ, процессор 8086 аппаратно отбрасывал лишний бит и возвращал их в начало первого мегабайта, то есть было фундаментальное ограничение размера ОЗУ процессором. Процессор 80286 этого не делал и лез по адресу выше 1 МБ. Это ломало старый софт.
Решением стал логический вентиль на 21-ю линию (A20), который по умолчанию был выключен. Чтобы твое ядро могло использовать всю оперативку, а не только первый мегабайт, эту линию нужно активировать вручную как в boot.asm. В real mode адрес вычисляется как segment * 16 + offset, это означает что максимальный адрес может быть 0xFFFF:0xFFFF. В десятичном виде это 65535 * 16 + 65535 = 1,114,095 байт (чуть больше 1 МБ). Т.е. если A20 выключена то 21-й бит адреса аппаратно игнорируется. Адрес 1,000,500 превращается в 000,500. Процессор wrap-around'ится в начало первого мегабайта. Но если A20 включена то процессор видит разницу между 000,500 и 1,000,500. В текущем `boot.asm` сначала идёт проверка через сравнение двух адресов. Если разные — A20 уже включен. Если нет — включаем через BIOS `int 0x15` с `AX=0x2401`. Способ через клавиатурный контроллер `0x64/0x60` тоже классика, но сейчас в коде выбран более короткий BIOS-вариант.

---

- **GDT (Global Descriptor Table)**

Это таблица которая объясняет процессору как сегментирована память. Если в 16-битном пространстве Real mode мы придерживались формуле segment * 16 + offset, то в 32-битном пространстве Protected mode сегментные регистры cs, ds, ss уже не содержат адреса. Они содержат селектор — то есть индекс в таблице GDT. Можно заметить что Base (базовый адрес) и Limit (размер) разбросаны по разным байтам дескриптора:
1) Base разбит на: 2 байта (dw), 1 байт (db) и еще 1 байт (db).
2) Limit разбит на: 2 байта (dw) и 4 бита внутри байта Granularity.

Когда Intel переходила с 16-битного 80286 на 32-битный 80386, им нужно было сохранить обратную совместимость. Они не могли просто взять и расширить дескриптор, поэтому костыльно впихивали новые биты адреса в пустые места старого формата. В итоге получился винегрет который мы видим в коде. Может есть более красивое решение, но я честно не нашёл и не врубился всецелом. И так по порядку:

Нулевый дескриптор `dq 0x0000000000000000` — процессор требует, чтобы первый дескриптор всегда был заполнен нулями. Если случайно забыть инициализировать сегментный регистр (он будет равен 0) и попытаешься обратиться к памяти, процессор увидит что ты пытаешься использовать нулевый селектор и выбросит исключение. Это защита от багов. У меня используется Flat Model: Base = 0x00000000, Limit = 0xFFFFFFFF — сегменты кода и данных накладываются друг на друга и покрывают всю доступную память. По этому же принципу работают виндовс и линух, т.к. реальное разграничение памяти сейчас делается через Paging, а не через сегментацию.

*   gdt_descriptor — процессору нужно знать где лежит таблица. Для этого есть специальная инструкция lgdt. Она принимает на вход адрес структуры с размером таблицы и её физическим адресом.*

*   Селекторы CODE_SEG и DATA_SEG — это смещения внутри GDT. Каждый дескриптор занимает 8 байт. 0x00 — Null; 0x08 — Code; 0x10 — Data.*

- **Зачем нужен PMM?**

Когда компьютер включается, в нём есть оперативная память — допустим, 128 мегабайт. Это просто огромный массив байтов. Никто не следит за тем, какие части этого массива уже используются, а какие свободны. Ядро операционной системы должно само организовать учёт: вот этот кусок памяти занят под код ядра, вот этот — под данные, вот этот — свободен, можно отдать кому-нибудь. PMM — Physical Memory Manager — тот кто этим занимается. Его задача предельно проста: знать какие страницы памяти свободны, а какие заняты. Выдавать страницу по запросу и принимать обратно при освобождении.

Почему страницы, а не просто байты? Потому что управлять памятью побайтово дорого. Процессор работает с памятью блоками по 4KB — это называется страница. Как хранить информацию о том, какие страницы свободны? Самый простой способ — bitmap, где каждый бит отвечает за одну страницу. 32768 страниц = 32768 бит = 4096 байт = всего 4KB. В восемь раз экономнее чем по байту на страницу.

*   В этом проекте bitmap кладётся прямо в начало физического пула, то есть по адресу `kernel_end`, который приходит в `pmm_init` как `memory_start`. Верхняя граница пока жёстко `0x400000`, а страницы под сам bitmap сразу помечаются занятыми. Код ядра отдельно не надо отмечать в bitmap, потому что он лежит до `memory_start`.*

- **VMM (Virtual Memory Manager) и Paging**

После PMM, который работает с физическими страницами, нужен ещё один слой — VMM, который занимается виртуальными адресами. Смысл вот в чём: каждый процесс думает что у него есть собственные 4 ГБ памяти начиная с нуля. На самом деле это иллюзия — процессор прозрачно транслирует виртуальные адреса в физические через специальные таблицы.

Эти таблицы называются Page Directory и Page Table. Архитектура двухуровневая: Page Directory содержит 1024 записи, каждая из которых указывает на Page Table, а та в свою очередь тоже содержит 1024 записи — и каждая уже указывает на реальную физическую страницу 4KB. Итого 1024 × 1024 × 4KB = 4 ГБ адресного пространства.

Виртуальный адрес разбирается так:
- Биты 31:22 - индекс в Page Directory (10 бит)
- Биты 21:12 - индекс в Page Table (10 бит)
- Биты 11:0 - смещение внутри страницы (12 бит)

Чтобы включить paging, нужно: создать Page Directory, замаппировать нужные страницы, записать адрес PD в регистр CR3, и выставить бит PG (31-й) в регистре CR0. После этой инструкции все адреса начинают транслироваться, включая тот код который эту инструкцию только что выполнил. Поэтому перед включением paging'а нужно обязательно замаппировать код ядра identity (virtual == physical), иначе следующая же инструкция вызовет page fault и всё упадёт.

*   VGA буфер по адресу 0xB8000 тоже нужно замаппировать отдельно, иначе экран перестанет работать после включения paging'а.*

*   TLB (Translation Lookaside Buffer) — это кеш трансляций в процессоре. При анмаппировании страницы нужно сбросить её запись в TLB через инструкцию invlpg, иначе процессор может использовать устаревшую трансляцию.*

- **kheap**

PMM выдаёт целые page'ы по 4KB. Это удобно для крупных аллокаций, но неудобно если нужно выделить 100 байт, тратить ради этого весь page тупо. Для этого поверх PMM сделан kheap. Это хип ядра с kmalloc/kfree.

Устроено это через linked list блоков. Каждый блок в памяти начинается с заголовка `block_header_t` где хранится размер блока, флаг занятости и указатели на соседние блоки. При kmalloc ищем первый подходящий свободный блок, если нашелся таков то отдаём. Если нет расширяем кучу с помощтю новых pageв. При kfree помечаем блок свободным и склеиваем его с соседними свободными блоками. Куча растёт от 0x400000 до 0x4000000 (64 MB --- пока что).

*   Все аллокации выравниваются на 16 байт, это требование многих алгоритмов и SIMD инструкций*

*   Coalesce - это по сути объединение соседних свободных блоков. Он уже есть в kheap, чтобы долгоживущие аллокации меньше фрагментировали память.*

- **VGA driver**

Текстовый режим VGA это по своей сути буфер по адресу 0xB8000. 80 × 25 = 2000 ячеек по 2 байта каждая. Младший байт аски символ, старший - атрибут цвета. Цвет упаковывается в один байт:: биты 3:0 - foreground 16 цветов, биты 7:4 — background 16 цветов. Все в лоб, если хочешь вывести символ то записывай в нужную ячейку. Никаких сисколов, никакого посредника

Курсор управляется через порты 0x3D4/0x3D5, индексный и дата регистры CRT контроллера соответственно. Позиция курсора равна y × 80 + x, передаётся как два байта через регистры 0x0E (верхний) и 0x0F (нижний)

*   volatile uint16_t* на буфере очень важен, ибо без него компилятор может решить закешировать запись и вообще не отправить её в железо. volatile гарантирует что каждая запись действительно уйдёт по адресу, этой конструкции будет довольно много в проекте*

- **Keyboard**

Клавиатура работает через PS/2 контроллер. На порт 0x60 приходят данные, читать scancode, порт 0x64 это статус. Бит 0 в статусном регистре означает что в буфере есть данные для чтения. Важно омтетить что Scancode это не ASCII, это номер физической клавиши. Таблица трансляции scancode -> ASCII хранится прямо в коде (US QWERTY раскладка)
Key release события отличаются от key press тем что бит 7 scancode установлен. То есть нажатие 'A' даёт 0x1E, а отпускание — 0x9E.

Внутри драйвера сделан circular буфер на 256 элементов. keyboard_handler пишет в него из прерывания, а читается он из основного кода. Пока IDT не настроена значит keyboard_handler вызвать невозможно. Но keyboard_getchar через hlt-loop будет работать как только прерывания появятся

*   Через тот же контроллер клавиатуры, порт 0x64, часто включают A20. В текущем bootloader'е используется BIOS `int 0x15`, но помнить про вариант через keyboard controller полезно — в x86 таких исторических крючков вагон.*

- **Timer и PIC**

PIC - Programmable Interrupt Controller : это микросхема которая управляет прерываниями. В IBM PC их две штуки: мастер (oldschool) PIC1 и слейв PIC2, касдкадные через линию IRQ2. Всего они обрабатывают 16 линий прерываний IRQ 0–15

Проблема следующая: по умолчанию IRQ 0–7 мапятся на прерывания 0x08–0x0F, а это как раз зона эксептов процессора (деление на ноль, page fault и т.д.). Коллизия. Поэтому одно из первых что нужно сделать - перемапить PIC. Делается это через последовательность команд инициализации ICW1-ICW4 в порты 0x20/0x21-мастер и 0xA0/0xA1-слейв. После ремапинга IRQ 0–7 становятся прерываниями 0x20–0x27, а IRQ 8–15 0x28–0x2F. В моем проекте PIC ремаппится в timer.c.

PIT (Programmable Interval Timer) - это таймер который тикает с фиксированной частотой. Базовая частота 1.193182 МГц, делится на делитель который мы сами задаём. Хотим 100 тиков в секунду значит пишем делитель 11932 в порт 0x40. По каждому тику прилетает IRQ0 -> прерывание 0x20 -> вызывается timer_handler.

*   После каждого обработанного прерывания нужно отправить End Of Interrupt - EOI командой 0x20 в порт PIC, иначе контроллер думает что прерывание ещё обрабатывается и блочит все последующие*

---

- **Disk (ATA PIO)**

Жёсткий диск подключается по интерфейсу ATA (он же IDE). Режим PIO (Programmed I/O) самый простой. CPU сам читает/пишет данные через порты ввода-вывода 0x1F0–0x1F7. Медленно и не спеша, с некой иронией, но зато понятно и не требует DMA.

Адресация через LBA28 Logical Block Addressing: диск воспринимается как плоский массив секторов по 512 байт. LBA28 это 28 битный номер сектора, что даёт адресацию до 128 ГБ (2^28 × 512 байт).

Последовательность чтения: выбрать диск -> записать адрес сектора по кускам в регистры 0x1F3 – 0x1F6 -> послать команду READ (0x20) в 0x1F7 -> ждать бит DRQ в статус регистре -> читать 256 слов через inw(0x1F0) = 512 байт.

Команда IDENTIFY (0xEC) позволяет узнать всё о диске: модель, серийник, размер. Контроллер возвращает 256 слов с информацией. Что интересно, так это то что строки там хранятся побайтово переставленными, это legacy с древних времён ATA

*   DRQ (Data Request) — это бит в статусном регистре означающий что контроллер готов отдать данные. Читать раньше чем он установится — бессмысленно.*

*   Команда `disk` в терминале вызывает ATA IDENTIFY и показывает найденные primary master/slave устройства.*

---

- **IDT (Interrupt Descriptor Table)**

IDT - это аналог GDT но для прерываний. GDT объясняет процессору как сегментирована память, IDT объясняет что делать когда происходит прерывание или исключение. Таблица на 256 записей состоит из 32 исключения процессора (деление на ноль, page fault, general protection fault и тд) + IRQ от устройств + программные прерывания

Каждая запись в IDT это дескриптор прерывания: адрес обработчика, сегмент кода, флаги (тип шлюза, уровень привилегий). Когда происходит прерывание, процессор смотрит в IDT, берёт адрес обработчика и прыгает туда, предварительно сохранив состояние (pushad + сегментные регистры) на стеке.

В проекте уже есть ISR/IRQ stubs в ассемблере, заполнение IDT, `lidt`, ремап PIC и включение `sti`. Благодаря этому таймер и клавиатура работают через настоящие IRQ, а терминал может жить в обычном цикле с `hlt`, просыпаясь по прерываниям.

*   Как процессор работает с памятью? (из книги Макарова и Насырова)*
*   В процессорах начиная с i386 базовые регистры стали 32-битными, что позволяет адресовать до 4 гигабайт. Сегментные регистры остались 16-битными, но в защищённом режиме они не содержат адреса — они содержат индекс дескриптора. Таблица дескрипторов представляет собой массив записей по 8 байт, где описываются адреса, пределы и права доступа к сегментам. При обращении за пределы сегмента процессор генерирует исключение. При обращении к сегменту из дескриптора берётся базовый адрес и складывается со смещением — получается линейный 32-битный адрес. Для i386 и выше этот линейный адрес проходит ещё через трансляцию paging'а и становится физическим.*

- **Bootloader, DAP и почему kernel.bin flat**

Boot sector по классике должен влезть в 512 байт, причём последние два байта обязаны быть `0x55AA`, иначе BIOS даже не будет считать сектор загрузочным. Из этих 512 байт надо успеть поставить стек, сохранить номер диска, включить A20, загрузить ядро, подготовить GDT и прыгнуть в protected mode. Места мало, поэтому любой лишний мув быстро аукается

Ядро сейчас грузится через BIOS Extended Read т.е. `int 0x13`, `AH=0x42`. Для этого используется Disk Address Packet это такая маленькая структура где лежит количество секторов, segment:offset буфера и LBA. В проекте bootloader читает по одному сектору, двигая segment на `0x20`, потому что 512 байт / 16 = 32 пейджа

`kernel.bin` — это плоский бинарь т.е. не ELF, не PE, не какой-то ещё формат, а просто байты кода и данных подряд. Линкер скрипт говорит линкеру тип асчитай что ядро живёт с `0x10000`. Bootloader грузит туда байты и прыгает. Это просто и понятно, однако есть нюанс - нельзя нормально прочитать секции, символы, entry point из заголовка, размер ядра и прочую полезную инфу

---

- **Linker script и символ kernel_end**

`kernel/linker.ld` это штука которая решает где в памяти окажутся `.text`, `.rodata`, `.data`, `.bss`. В проекте старт выставлен так:

        . = 0x10000;

Это значит что все адреса внутри ядра будут рассчитаны так, будто код реально лежит с `0x10000`. Если bootloader загрузит ядро куда-то ещё, всё посыпется, потому что flat бинарь не умеет сам себя релочить.

После `.bss` linker script выставляет:

        kernel_end = ALIGN(4096);

Этот символ нужен уже Си коду. `memory_init()` берёт `&kernel_end` как нижнюю границу свободной физической памяти. Идея простая: всё что ниже — boot/kernel/данные ядра, туда PMM не лезет. Всё что выше — потенциально можно раздавать страницами, если оно вообще usable.

- **Serial logging**

Serial порт COM1 живёт по базовому адресу `0x3F8`. В эмуляторе это почти чит-код для дебага: можно писать байты в порт и видеть их в терминале хоста. Поэтому `terminal_write()` сейчас дублирует символы и в VGA, и в `serial_write(COM1, ...)`.

Инициализация выглядит примерно так: отключить interrupts на UART, включить DLAB, записать divisor для baud rate, поставить формат 8N1, включить FIFO, поднять DTR/RTS. В коде это `serial_init(COM1, 115200)`. Если VGA сломан, serial часто всё ещё живой. Если serial тоже молчит значит мы умерли раньше

*   Для QEMU удобно использовать `make run-serial`: окно VGA не открывается, а всё что ядро пишет в COM1, летит прямо в stdout.*

- **Mini clib**

В обычной программе мы подключаем `stdio.h`, зовем `printf`, и где-то там операционка/рантайм все делают. В freestanding kernel такого нет и компилятор может собрать C, но стандартная libc не обязана существовать, сисколов тоже не существуют, файловых дескрипторов по настоящему нет

Поэтому в `clib/` лежат свои минимальные реализации функций `memset`, `memcpy`, `strlen`, `strcmp`, куски `printf/snprintf`, `atoi` и т.д. Это не прям полноценная libc, но минимальный набор есть, в свободное время можно просто копипасть glibc 

*   `malloc/free` из `clib/src/stdlib.c` сейчас живут на статическом буфере 64 KB. Для ядра лучше использовать `kmalloc/kfree`, а clib malloc потом либо привязать к kheap, либо оставить только для очень раннего/тестового режима.*

- **Page fault**

Page fault это exception 14. Он случается когда paging включён и процессор не может нормально транслировать виртуальный адрес например когда страницы нет, прав не хватает, запись в read-only, user code полез в supervisor page и т.д.

У page fault есть две крайне полезные вещи:

 - `CR2` виртуальный адрес, на котором процессор споткнулся.
 - `err_code` битовая маска причины.

Биты `err_code` в простом виде:

 - bit 0 `P` 0 значит страницы не было, 1 значит страница была, но нарушены права.
 - bit 1 `W/R` 1 если ошибка на записи.
 - bit 2 `U/S` 1 если ошибка пришла из user mode.
 - bit 3 `RSVD` зарезервированные биты в page table/page directory были выставлены неправильно.
 - bit 4 `I/D` ошибка при fetch инструкции, если CPU поддерживает этот флаг.

Сейчас ISR просто печатает название исключения. Следующий качественный апгрейд — отдельный handler для int 14, который пишет `CR2`, `err_code`, `EIP`, `CS`, `EFLAGS` в serial. Это резко сократит время дебага paging'а и kheap'а.

- **E820 memory map**

Сейчас память в ядре задаётся руками от `kernel_end` до `0x400000`. Это норм чтобы стартануть PMM, но реальная память PC не является непрерывным массивом от нуля до N-1. Там есть BIOS области, VGA, ROM, ACPI, MMIO, дырки, странные legacy-участки и прочие ништяки архитектуры

BIOS E820 отдаёт карту памяти списком записей - base, length, type. Type 1 обычно означает usable RAM, остальные типы лучше не трогать без понимания. Bootloader должен собрать этот список в real mode, положить его в известное место и передать ядру указатель/количество записей. Потом PMM сможет добавлять в bitmap только реальные usable pages, а всё занятое помечать reserved.

Диск сам по себе мало полезен, если с ним можно говорить только секторами. Сектор 123 прочитать можно, а вот "открой `/etc/test.txt`" уже нет. Для этого нужна фс

Минимальный флоу такой:
 - block device layer: читать/писать сектор без знания ATA деталей
 - filesystem driver: понимать структуру конкретной ФС
 - VFS: общий интерфейс `open/read/write/close/stat`, чтобы shell и будущие программы не знали FAT там снизу, tarfs или что-то своё

- **User mode и syscalls**

Пока весь код живёт в ring0, то есть в режиме где можно всё. Это пока норм для старта, но это не каноничная ОС. User mode нужен чтобы пользовательская программа не могла случайно записать в page table, повесить PIC или стереть нахрен само ядро. Для этого нужны отдельные сегменты ring3 в GDT, страницы с флагом `PAGE_USER`, TSS для kernel stack при переходе из user в kernel и механизм syscall'ов.

Самый простой syscall на старте это прерывание `int 0x80`. User program кладёт номер syscallа в регистр, аргументы в другие регистры, вызывает `int 0x80`, CPU переходит в kernel handler, ядро проверяет аргументы и делает работу. Например `write(1, buffer, len)` может печатать в терминал.

До syscalls лучше дойти после FS и нормальной памяти. Иначе получится что у нас есть user mode, но запускать там нечего, зато есть сискол))
